# Configuration reference

Run these commands on the host:

```bash
sandbox config          # Effective configuration
sandbox config schema   # All fields, defaults, and merge rules
```

Unknown TOML keys are rejected.
The schema describes your installed version.
The [user template](../templates/config.toml) and [project template](../templates/project-config.toml) show setup examples.

## Paths

These guides use two placeholders:

- `{config}`: the Sandbox configuration directory.
  By default, `~/.config/sandbox` on macOS and Linux, or `%APPDATA%/sandbox` on Windows.
  `XDG_CONFIG_HOME` changes the configuration root.
  `SANDBOX_CONFIG_DIR` overrides the complete Sandbox configuration directory.
- `{data}`: `~/.local/share/sandbox` on macOS and Linux, or `%APPDATA%/sandbox` on Windows.
  If `XDG_DATA_HOME` is set, use `$XDG_DATA_HOME/sandbox` instead.

If you set `SANDBOX_CONFIG_DIR` or the XDG variables, use those paths instead.
On Windows, `{config}` and `{data}` use the same directory by default.

Files you can edit:

- `{config}/config.toml`: personal configuration for all projects.
- `{config}/docker/Dockerfile`: personal tool image.
- `{config}/settings/`: sources for shared settings.
- `.sandbox/config.toml`: project configuration.
- `.sandbox/docker/Dockerfile`: project tool image.

Create user files with `sandbox init`, or project files with `sandbox init --project`.
When a guide shows a list, add entries to the existing list rather than adding the same TOML key twice.
Keep unrelated entries unless you intend to remove them.
See [updates](UPDATES.md) to review newer templates without resetting your setup.

## Precedence and merge rules

Configuration applies in this order:

```text
Built-in defaults -> user config -> trusted project config -> CLI flags
```

Single values use the last specified value.
Arrays accumulate, so a project can add network domains or mounts but cannot remove user entries.
Change an array in the file that defines the unwanted item.

Host-command rules are combined in user-then-project order.
Duplicate patterns keep the first rule.
Rule tests run before duplicate removal.
Nested configuration values override earlier values rather than merging recursively.
Platform conditions are not supported in TOML.

## Fields

Built-in arrays are empty.
The files generated by `sandbox init` add tools' settings, persistence, mounts, and a broad developer-service network allowlist.

### Runtime and access

- `runtime`: `"docker"`, `"podman"`, or `"apple-container"`.
  If unset, Sandbox detects them in that order.
- `runtimes`: runtime-specific options.
  Currently `[runtimes.apple-container]` accepts `dns = "default"`, `"host"`, or `"host-ipv6"`.
  Default: `"default"`.
  See [Apple settings](APPLE-CONTAINER.md).
- `readonly`: make the project mount read-only.
  Default: `false`.
  Other writable mounts remain writable.
- `clipboard`: `"enabled"` or `"disabled"` for attached sessions.
  Default: `"enabled"`.
  See [clipboard access](CLIPBOARD.md).
- `full_network`: allow unrestricted outbound access.
  Default: `false`.
- `no_proxy`: disable the managed proxy.
  Requires `full_network = true`.
  Default: `false`.
- `shm_size`: optional shared-memory size, such as `"2g"`, for tools such as Chromium.

### Lists

- `env`: session environment entries.
  Use `"NAME"` for host passthrough or `"NAME=value"` for an assignment.
- `mounts`: additional host paths.
  Examples: `"~/.aws:ro"`, `"/source:/destination:rw"`.
  Default mode: read-only.
  See [mounts](MOUNTS.md).
- `ports`: published container ports.
  Formats: `"3000"`, `"8080:80"`, or `"127.0.0.1:9090:9090"`.
  Interface support depends on the runtime.
  For network exposure, check the runtime's behavior.
- `allow_network`: allowed outbound domains and ports.
  Example: `["api.example.com", "git.example.com:{22,443}"]`.
  See [network access](NETWORK-FIREWALL.md).
- `allow_host_commands`: structured argument-matching rules.
  See [host commands](HOST-COMMANDS.md) for exact syntax and risks.
- `settings`: strings or tables with `path` and optional `mode`.
  Modes: `"mount"` (default) or `"copy"`.
  See [shared settings](SETTINGS-SYNC.md).
- `persist_paths`: tables with required `path` and optional `default`, `global`, `only_if_exists`, or `use_named_volume`.
  See [persistence](PERSISTENCE.md) for combinations and storage scope.

## Session environment

`env` applies to shells, commands, and their child processes, not container startup services.
`sandbox container start` creates no session and does not apply it.

```toml
env = ["ANTHROPIC_API_KEY", "DEBUG=1"]
```

Host passthrough skips unset values.
Empty values are preserved.
For each name, the last user, project, or CLI assignment wins.
Automatic terminal values and Sandbox-managed values can override these assignments.

These names are reserved and cause a configuration error:

- `SANDBOX` and names starting with `SANDBOX_`.
- `CLAUDE_CODE_SSE_PORT`.
- `DISPLAY`, `X11_AVAILABLE`, and `XAUTHORITY`.
- `WAYLAND_DISPLAY` and `WAYLAND_SOCKET`.

Changing `env` does not rebuild images or prevent container reuse.
New processes get the new values.
Existing processes, including shared tmux servers, keep their previous environment.
Direct runtime `exec` commands do not receive Sandbox session values.

Session environment is not a secret-isolation boundary.
Other processes in the same container can have access to session secrets.

## CLI overrides

Common options for a single run:

```bash
sandbox --readonly run claude
sandbox --mount /data:ro --env DEBUG=1 run claude
sandbox --port 3000 --allow-network api.example.com run claude
```

Use `sandbox --help` for the full option list.
Use `sandbox run --help` for run-only options such as `--silent`.
